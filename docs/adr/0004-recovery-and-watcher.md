# ADR 0004：恢复快照与当前文件外部变更监视

- 状态：Accepted（Phase 1）
- 日期：2026-11-21
- 决策者：Gather maintainers
- 相关：ADR 0003（写入、字节保真与冲突拒绝）

## 背景

ADR 0003 保证了“保存时不静默覆盖”，但还有两个丢稿窗口：

1. 用户持续编辑、尚未保存时进程被杀或断电，编辑内容只存在于内存。
2. 文件在打开期间被其他程序改写，用户直到按保存才知道；如果误点“覆盖”，体验很差。

Phase 1 的退出条件要求：模拟杀进程后至少恢复到最后一次自动保存，原文件不被破坏；外部修改必须有提示，不能静默覆盖。

## 决策

### 1. 自动恢复快照，而不是静默改写原文件

未保存内容写入 `app.getPath('userData')/recovery`，不碰用户文稿。理由：

- “自动写入原文件”会绕过用户的保存决定，也会和冲突检测互相打架。
- 快照是崩溃恢复的最后一道保险；用户仍通过显式保存把内容写回文稿。
- 原文件不被修改，误判时最多是多一份可丢弃的快照。

快照文件是带版本号的 JSON：

```json
{
  "version": 1,
  "id": "<路径 SHA-256 或 untitled-uuid>",
  "path": "C:\\notes\\draft.md",
  "name": "draft.md",
  "content": "LF 文本",
  "format": { "bom": false, "eol": "crlf" },
  "baseVersion": { "mtimeMs": 0, "size": 0, "digest": "..." },
  "savedAt": "2026-11-21T08:11:28.397Z"
}
```

- 有路径的文件使用规范化路径（Windows 统一分隔符与小写）的 SHA-256 作为稳定 ID；同一文件的新快照覆盖旧快照。
- 未命名文稿使用 `untitled-<uuid>`，恢复后仍以未命名状态进入保存对话框。
- 内容统一为 LF、剥离 BOM，格式单独保存；恢复后仍按原格式编码。
- 写入使用同目录临时文件 + `fsync` + `rename`，文件权限 0600（POSIX），失败清理临时文件。
- 列表读取时跳过损坏/半写快照，不阻塞其他恢复；ID 必须与文件名一致。
- 最多保留 20 份，超出按 `savedAt` 删除最旧。
- 保存成功、显式丢弃、载入磁盘版本后清理对应快照；打开另一个文件**不**自动删除旧快照。

### 2. 快照节奏

- 停止输入约 2.2 秒后写一次。
- 持续输入时每 15 秒强制写一次。
- 保存进行中暂停快照；保存成功后使在途快照失效，避免“保存后又被旧快照复活”。
- 保存期间用户继续输入时，保存结果不会把新输入误标为已保存；界面保持脏状态并安排新快照。

这不是逐键持久化。极端情况下最近约 2.2 秒的输入可能不在快照里；该边界必须对用户可见，而不是宣称“永不丢字”。

### 3. 启动恢复界面

- 渲染层启动时请求 `recovery:list`，只拿元数据，不加载全部正文。
- 横幅列出文件名、时间、格式与路径；提供“恢复”和“丢弃”。
- 恢复时才 `recovery:read` 取正文；若当前有未保存内容，先确认。
- 恢复后进入脏状态，仍需用户主动保存；不会自动覆盖磁盘。
- 恢复路径时调用 `recovery:activate`，让 watcher 进入该文件；未命名快照则停止旧 watcher。

### 4. 当前文件 watcher

主进程只监视一个活动文件：

- `fs.watch` 监听父目录并按 basename 过滤，兼容编辑器“写临时文件再 rename”的保存方式。
- 每 2 秒做一次 stat 轮询，作为 `fs.watch` 漏事件的兜底。
- 事件先对比 `size`/`mtimeMs` 快速跳过未变化；需要时读取文件并计算 SHA-256，确认后才通知。
- 自身保存或重载后调用 `updateVersion`，旧事件因 digest 相同被忽略。
- 外部变化会更新 watcher 的 expected 版本，避免同一变化反复弹窗；再次变化会再次通知。
- 文件被删除/移动时通知 `removed`；重新出现后可以再次通知 changed。
- 渲染层只接受当前路径的事件；未命名文稿不接受任何旧 watcher 事件。
- 通知不自动覆盖编辑器，也不自动重载；用户显式选择“载入磁盘版本”或“另存为”。
- 载入磁盘版本前若编辑器脏，先确认；重载后重建 `EditorState`、重置撤销栈，并清理该路径快照。

## 代价与约束

- 恢复快照未加密，内容位于本机 userData；依赖操作系统账户权限与磁盘加密。
- 最多 20 份，不能替代版本历史；没有 diff/合并，外部变化只能整体选择。
- 2.2 秒/15 秒节奏是安全与写盘成本的折中；大文件频繁输入时每 15 秒的写盘仍需性能测试。
- `fs.watch` 在不同文件系统与发行版上行为不完全一致，因此必须保留轮询；轮询仍有最长约 2 秒的发现延迟。
- 快照写盘失败目前只更新状态文本，不会阻塞编辑；ENOSPC/EACCES 已由注入测试覆盖，真实磁盘满/只读目录矩阵尚未完成。
- 关闭窗口时 `beforeunload` 只提示，不保证同步刷快照；最近输入仍受节奏限制。

## 验证

- `apps/desktop/test/recovery.test.ts`：路径/未命名快照、覆盖、列表、读取、丢弃、损坏文件、写删串行与写入失败隔离。
- `apps/desktop/test/file-watcher.test.ts`：外部修改、自写忽略、删除与重建、轮询差异。
- `apps/desktop/test/atomic-write.test.ts`：ENOSPC/EIO/EACCES 与 sync/rename 失败清理。
- Windows 生产窗口手工验证：
  - 打开文稿、输入后等待快照；原文件未改变。
  - `taskkill /F` 强杀后重启，恢复横幅出现；恢复内容正确。
  - 恢复后保存，原文件写入且快照清理。
  - 未命名文稿快照可在重启后恢复，并通过另存为落盘。
  - 外部改写/删除被实时提示；载入磁盘版本成功。
  - 打开另一文件后，旧未保存快照仍保留。
- CI：Ubuntu/Windows Node 24，63 个测试、构建与 CLI 冒烟（恢复批次基线 44885022294；本批运行待补）。

## 未解决

- 冲突逐段合并、版本历史。
- 快照加密与保留期策略。
- 磁盘满、只读目录、断电模拟。
- 多窗口/多工作区。
- 5 MiB 文档快照性能。
